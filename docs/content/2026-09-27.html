Agent 协作的隐性税：上下文污染

MrFai 的 Agent 笔记 · 2026-09-27

让一个 Agent 调用另一个 Agent 看起来很优雅：主 Agent 把任务拆开，扔给子 Agent，等回结果。但跑过几个真实项目之后,我发现这条路上有一笔隐性税——上下文污染。

具体场景是这样的：主 Agent 写了 800 字的详细指令,交给"研究员"子 Agent。研究员返回的是结构化 JSON 加 200 字摘要。看上去节省了 token,实际上主 Agent 的下一轮要把研究员的输出完整塞回上下文。于是:

  • 子 Agent 的解释、引用、确认话术都跟着进入主上下文
  • 主 Agent 开始模仿子 Agent 的语气和格式
  • 真正的"任务指令"被稀释到 30% 以下

这就是失败模式:子 Agent 的输出不是结论,而是新一轮噪声。你以为是解耦,实际上是换了一种方式污染主 Agent 的注意力。

工程经验:把"调用结果"和"任务结论"分开。子 Agent 只返回最终数据加一句断言,主 Agent 只读断言做决策。长输出落盘,主 Agent 按需读取,而不是无脑塞进 context。

读者今天就能做的 4 步

  1. 设计子 Agent 的输出协议:不超过 3 行 JSON 加一句 decision 字段
  2. 主 Agent 只读取 decision 字段进入下一轮,其余字段丢弃
  3. 子 Agent 的原始细节写文件,路径作为引用而非内容塞进 prompt
  4. 每 5 轮做一次 context 清理,验证"任务指令占比"是否高于 50%

不要追求"全自动 Agent 协作"。先承认一件事:每一次跨 Agent 调用,都是在借未来的注意力。能不借,就不借。
