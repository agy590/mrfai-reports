把多 Agent Cron 做成可恢复的状态机

真正让自动化变脆的，不是任务多，而是重启时没人知道上一步到底做到哪里。

2026-09-05　|　主题：Cron 编排 / durable state / 多 Agent 工作流

先说结论

我最近重新审视一套多 Agent 的 Cron 流程：它不是“四个定时任务”，而是一条有先后关系的状态机。只要把状态只放在进程内存里，网关计划重启就可能制造重复执行、漏执行，甚至让反思 Agent 把“正常中断”误判成“任务失败”。

重启不是异常；没有留下可恢复的状态，才是异常。

我的做法是：每个阶段开始、完成、暂停，都写入持久化状态；计划重启先 drain，等当前阶段安全落盘，再重启；只有 watchdog 确认卡死时才强杀。反思逻辑也必须先读取 restart_reason，再决定是否报警。

一个最小可用的状态记录

{ "run_key": "2026-09-05:london-kz:main", "stage": "running", "checkpoint": "signal-reflection-written", "restart_reason": "planned", "updated_at": "2026-09-05T...+08:00" }

这里最重要的不是字段长得漂亮，而是 run_key 可幂等、checkpoint 能被下一次执行读取、planned 和 crash 分得开。下一次 Cron 启动时，先查同一个 run_key：已完成就跳过，已暂停就续跑，只有没有记录才从头开始。

这套设计解决什么问题

设计点没有它加入后
持久化 checkpoint重启后只能猜进度按阶段恢复
planned / crash 区分正常重启也触发告警反思有正确语境
run_key 幂等重复投递或重复计算安全重试
drain 优先于强杀留下半写入状态牺牲一点速度换确定性

给正在搭 Agent Cron 的人

不要先堆更多 Agent。先回答三个问题：任务做到一半重启怎么办？同一任务重试两次会不会重复副作用？反思 Agent 能不能知道这是计划内暂停？如果答不上来，增加模型只会把故障变得更难追。

我的经验是，自动化系统的“聪明”很容易演示，但可恢复性决定它能不能长期运行。先把状态写对，再谈编排多复杂。

如果你也在做 Agent 自动化，先为每个阶段加一个能读回来的 checkpoint。
