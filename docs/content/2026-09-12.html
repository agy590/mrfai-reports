别把 Agent 当记事本 — 上下文腐烂是 Agent 工程里最常见的自杀方式

2026-09-12 · MrFai 的 Agent 笔记

Agent 的质量不是 prompt 长度决定的。上下文窗口不是越大越好, 这件事我是在一次复盘里真正挨了一拳才认的。

早期我让一个 research agent 把所有检索片段、历史结论、用户偏好一次性塞进上下文, 想让它"参考更全"。结果恰恰相反: 输出开始自相矛盾, 同一论据被同时用来支持相反的结论; 任务越复杂, 崩溃越快。这就是常说的 context rot: 信息越多, 模型对核心指令的注意力被稀释得越稀, 中段的细节最先失忆, 末尾的格式要求也被吞掉。

教训是简单的, 修起来却反复踩坑。后来我把它压成下面这套最小习惯, 至少让本地小模型不再"看似聪明地胡说":

  1. 分层记忆: 任务级只放当前任务的事实, 项目级放稳定约定 (例如输出格式), 长期记忆单独索引, 用的时候按需检索, 不要全量复制。
  2. 设上下文预算: 单次任务总输入不超过窗口的 40%, 剩下留给生成; 超过就截断最旧的检索片段, 而不是继续往里塞。
  3. 关键指令放首尾: 开头放目标, 结尾放格式与验收; 中间是噪声, 注意力最弱。
  4. 每完成一个子任务就压缩: 让 agent 自己用两三百字总结前一段, 再把摘要往下传; 旧摘要存档而不是反复回填。

Agent 工程里最难的部分不是模型, 是约束: 约束它记住什么, 约束它忘记什么。上下文不是免费的 buffer, 是要付费的认知带宽。

本文是个人工程笔记, 观点来自本地实验; 不同模型与版本行为会变, 不构成任何产品或投资建议。
