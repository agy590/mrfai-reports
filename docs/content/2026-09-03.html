撞过的最蠢也最隐蔽的坑

跑了好几个月的自动化 cron,我撞过最蠢也最隐蔽的坑:

用 terminal 的 heredoc 写多行文件,有时候会卡在 security pending_approval,整个任务直接断在那里。

有一次我让 agent 写一个约 80 行的 Markdown 报告,heredoc 一塞进去就 pending。一开始我以为是 shell escape 的问题,试了 quoting、转义、变量替换,没用。最后发现是安全层把 heredoc 内的某些关键字组合当成 prompt injection 风险,人工确认弹窗卡在那,根本没人接。

更惨的是:这玩意儿只在大文件 / 多行内容 / 包含某些结构时才触发,小段命令完全没事。等于说 bug 是概率触发的,本地测试跑 10 次都过,生产 cron 一上就翻车。

实测方案

3 个月前我把所有 cron 的「写文件」动作统一改成 write_file 工具,问题消失。

方案多行文件占位符检测syntax checkpending_approval 概率
cat > file <<EOF OK 写完手 grep 无 高
write_file 工具 OK 配合 grep .py/.json/.yaml/.toml 自动 lint 0%

write_file 不只是绕开 security gate,它还会对常见语言跑 syntax check,且只 surface 新错误。意思是你改了一个 .yaml,即使它之前就有 5 个 lint 警告,工具也只报你这次引入的新错 — 噪声直接砍 90%。

配套流程 (SOP)

  1. 内容生成走 LLM 输出 markdown 字符串
  2. write_file 落到项目 cron/output/<job_id>/<date>.md
  3. 同文件路径转 HTML 副本(供网页 / Telegram)
  4. 本地 grep / wc 自验证(占位符残留、文件大小、DOCTYPE)
  5. 最终回复只输出 3-5 行(标题 + 摘要 + 媒体链接)

第 5 步是关键:别在 final response 里贴长报告。Telegram 截断 + 双消息风险,HTML 投递走 MEDIA: 行就够了。

一句话总结

写文件优先工具,heredoc 留给一次性 shell 操作。

自动化场景里能少踩 90% 的隐形坑。
