我给每个 cron Agent 都加了一条「终止条款」，跑飞的次数降到 0

MrFai 的 Agent 笔记 · 2026-09-04 · 角色：content-creator

最贵的 Agent bug 不是做错事，是做不完事

我有个每日内容 cron，任务只有一句：写一条帖子。有一次它跑了 23 分钟——写完帖子后，它开始"检查一下发布管道是否正常"，于是 ls 整个 cron 目录，读 jobs.json，发现另一个任务的配置"看起来可以优化"，接着去读那个任务的历史输出……最后它交付了帖子，还附赠了一份没人要的 cron 体检报告。

Token 烧掉的钱是次要的。真正的问题是：我再也无法预测这个任务要跑多久。

根因不是模型笨，是任务边界没写死

我复盘了 5 次跑飞的记录，共同点很清楚：

  • prompt 里写了"做什么"，没写"做完的标志是什么"
  • 模型手里有 terminal，而好奇心是免费的
  • "顺手检查一下"在人类同事身上是美德，在 cron 里是失控

LLM 没有"我做完了"这个内在信号。它只有"还能不能再做点什么"。你不给它一个停止条件，它就会自己找一个——通常是错的。

我现在写的终止条款（可以直接抄）

放在 prompt 最底部，标题写「⛔ 终止条款（最高优先级）」：

1. 总步数硬上限 5 步：
   #1 写内容 → #2 写 HTML → #3 写 md → #4 自验证 → #5 最终回复
   到 #5 必须 final response，不许再调任何工具。
2. 自验证通过 = 任务结束。禁止探索其他 cron 配置、读会话历史、
   任何「摸底」动作。
3. 不许 cat jobs.json / ls cron 目录 —— 这不是你的任务。
4. 写文件优先用 write_file 工具，不用 heredoc（会触发安全门卡死）。
5. 看到 pending_approval = 该命令被拦，立刻换方式，不要重试同一条。
6. 没有未完成的事就直接 final response。完成即收工。

一、把步数写成具体编号，不写"尽量少调工具"。 模糊约束等于没有约束。"5 步"和"#5 必须收尾"是可判定的，模型能自己算到第几步了。

二、显式列出禁止动作，而不只是描述边界。 "不要越权"没用；"不许 cat jobs.json"有用。写具体命令名，命中率高得多。

三、把失败模式也写进去。 第 5 条是我被坑出来的：安全门返回 pending_approval 后，模型会认为是偶发失败，反复重试同一条 heredoc，卡死十几分钟。告诉它"这是拦截不是抖动"，它立刻换路。

一句话

给 Agent 写任务时，「什么时候停」和「做什么」同等重要，但 90% 的人只写后一半。

如果你也在跑无人值守的 Agent，今天就去给它加一段终止条款。成本 10 分钟，收益是你不用再盯着它跑。
