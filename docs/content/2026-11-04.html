多 Agent 不是多请几个人，是先把交接写成合同

2026-11-04 · 主题：多 Agent 协作

不少人把多 Agent 协作理解成「多找几个模型投票」。真跑一段时间就会发现，瓶颈从来不在模型不够聪明，而在交接边界没画清楚。Agent 之间传的是一段话，不是一份可验证的成果，链条越长，猜测被放大的速度越快。

我踩过的具体坑：三个 Agent 同时往同一个共享目录写分析产物，谁都没先占位，文件被反复覆盖。更糟的是下游读到的结论没有来源，等于在猜。后来我把规则改成「单一事实源 + 路径级租约」，同一时间只有一个 Agent 拥有某个路径的写权限，其余只读不写，覆盖就消失了。

另一类失败更隐蔽：Agent A 汇报「已完成」，但没留下任何可复现的证据；Agent B 基于这句话继续推进，把一个假设当成了事实。这类问题不需要更强的模型解决，只需要交接格式固定。

如果你也想跑多 Agent 协作，可以照这四步做：

  1. 先定唯一事实源。选定一个明确的产物路径或文档作为结论来源，其余输出只能追加、不能覆盖；没有 SSOT 的协作，本质上是并行猜测。
  2. 写前先领取租约。动手前声明自己负责的路径或条目，其他 Agent 不碰；租约释放前不算完成。
  3. 交接用四件套。证据（跑过的命令或可查链接）、已做的决定、当前阻塞、下一步动作。缺任何一项，交接即视为未完成。
  4. 验收靠复现，不靠「看起来对」。让接收方重跑一次验证命令再标记完成；跑不通就是没完成。

说到底，多 Agent 的产出上限不由 Agent 数量决定，由交接契约的严格程度决定。人带团队是这样，Agent 之间更是这样。
