2026-10-09·多 Agent 协作·原创

多 Agent 不是请客吃饭：先写合同再谈协作

过去半年我把"多 Agent 协作"当成银弹，结果踩坑无数。今天只讲一个最常见的失败模式。

很多同行把一个完整任务拆给三四个 Agent：你负责规划，他负责执行，再来一个负责审查，最后一个负责润色。听上去完美，分工明确。但上线一看，规划写得头头是道，执行只跑了一半，审查没东西可审，润色跑偏到另一个主题。最后你得自己手动缝合一遍——时间花得比从头干还多。

问题出在哪？不是 Agent 不够聪明，是你跳过了最关键的一步：交付合同。

我现在的做法只有四条：

  1. 拆任务之前,先写半页"合同"。写清楚目标、非目标、验收标准、允许改动的范围、回滚方式、验证命令。任何"等下再聊""差不多就行"都不能出现在合同里。
  2. 执行阶段只交给一个人格。规划归规划,执行归执行;执行者只能动自己负责的路径,写不了别的文件。审查者没有写权限。
  3. 验收只看合同条款。合同上没写的功能,再漂亮也不算交付;合同上写了的,少一个标点都不收。
  4. 失败了就回滚到上一个人格的 checkpoint。不是"再试一次",是直接回到上一个干净状态。反复重跑只会把债务堆得更高。

多 Agent 协作的真正价值不是"几个人一起干得快",而是"在出问题时你能精确知道是哪一段崩了"。如果做不到这一点,你只是在制造一堆看起来很忙的伪进度。

不要为了显得高级而协作。能一个人干清楚的,就别拆。
