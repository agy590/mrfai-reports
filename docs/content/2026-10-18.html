别信 Agent 的自述，去读文件

2026-10-18 · 主题：多 Agent 协作中的上下文失真

我给 Agent 立过一条硬规矩：动手前必须重新读盘，不要凭记忆改文件。理由不复杂——上下文是会话启动那一刻的快照，而磁盘上的文件在你上一次工具调用之后就已经变了。

真正的翻车场景是这样的：会话开始时我读了某个配置文件，于是整个上下文里都记着“阈值是 0.7”。半小时后，同一个仓库的另一个 Agent 为了配合上游接口，把它改成了 0.9。这时我让 Agent “把阈值改成 0.75 以适配现状”——它读的是记忆，不是文件，于是把改动写进了一个看起来完全合理的补丁里，覆盖掉了别人的修改，而叙述里还写着一句“已按当前配置调整为 0.75”。

更麻烦的是第三层：多 Agent 同时改一份共享文档时，谁都不知道谁已经动过。冲突不会报错，只会静默合并成一份谁都认不出来的产物。这比崩溃可怕得多。

我的结论很直白：Agent 的自述是意图，不是事实。事实只存在于文件系统里。凡是要写的地方，先读；写完再读一次；让验证结果而不是叙述来充当证据。

可以直接照做的四步

  1. 写之前 re-read。把目标文件当作唯一真相来源。哪怕三十秒前刚读过，也再读一次——多花一次工具调用，比回滚一次别人的改动便宜得多。
  2. 把规则放进文件，而不是留在对话里。项目约定写成仓库里的文档（约定、协议、命名），让每一个新会话、每一个 Agent 都能读到同一份，而不是靠某个人“记得”。
  3. 写完立刻读回验证。修改共享文件后重新读取目标段落，确认落地的就是你打算写的。工具说成功，和你看到它写进去，是两件事。
  4. 共享产物先领再写。多个 Agent 会碰同一份文件时，用一个简单的占用标记（谁、哪个路径、什么时候）避免交叉覆盖。写不动比写坏便宜。
