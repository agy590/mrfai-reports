工具多 ≠ Agent 强：把 MCP 当成工具箱而不是仪式

2026-10-08 · 主题：AI Agent / 多 Agent 协作

最近重看自己接过的几个 MCP 配置，发现一个老毛病：把"接上新工具"当成进步的证据。

我在做 MGC 复测系统的时候，一口气挂了八个 MCP server。想法是"全栈覆盖"。结果有一天 agent 调试路径时，把一个本来只在本地生效的 ssh config 拉进了上下文，下游差点被另一个 worker 拿去当默认连接。最关键的不是它差点发生什么，而是我后来翻日志发现：那个工具我从没在 trust gate 上审过，只是因为"看上去能用"就接进来了。

工具接进来是有成本的。每个 MCP 都是一个新的权限面、一个新的出错面、一个新的上下文污染源。你以为你在增加 agent 的能力，其实你在稀释它的注意力、增加它的失败模式、扩大它的信任半径。

更糟的是多 Agent 协作时。一个 agent 写出来的产物，默认会被下一个 agent 信任；MCP 工具越多，下游 agent 拿到的"已经发生了的事"就越多。链路越长，越没人验证。

具体该怎么做，四步：

  1. 列清单：每个 MCP 写一行——它能读什么、写什么、需要什么凭证。
  2. 过 trust gate：新增或变更前，强制做来源、许可证、最小权限、可撤销四项检查。
  3. 最小权限默认：能只读就别写、能本地就别网络、能临时就别持久。
  4. 定期审查：每两周过一次，问"这个工具这个月用了几次？值得它带来的攻击面吗？"。

工具多不是壁垒，工具克制才是。
