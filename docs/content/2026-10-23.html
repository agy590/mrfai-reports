多 Agent 协作：别让 Agent 自己给自己打分

2026-10-23·多 Agent 协作 / 工程方法

多 Agent 协作里，最贵的一课不是换更强的模型，而是别让 Agent 自己给自己打分。

我现在判断一个子任务是否完成，只看一件事：有没有一条可执行的命令能证明它成立。Agent 说「改好了、测试通过」几乎不算证据——不是它故意撒谎，而是它的自述和磁盘上的真实状态之间天然有缝隙：文件只改了一半、写进了另一个路径、测试跑的是旧版本、边界情况根本没被触发。我见过一次协作任务，三个 Agent 依次汇报「全部完成」，最后仍因一处路径前缀写错而整体失败，而真正的证据只需要一条 ls 就能拿到。

所以我把规则改成：完成 = 外部命令的退出码，而不是自然语言的自我确认。

具体四步

  1. 先定义验收命令，再动手。 任务描述里写清用什么命令判定成功（跑测试、grep 关键改动、构建一次、curl 一个接口），退出码为 0 才算数。说不清用什么命令验收的需求，通常说明需求本身还没想清楚。
  2. 交接只传三样东西。 改了哪些文件、命令原文与真实输出（包括失败的输出）、以及明确还没做的部分。省略「输出」就等于省略证据。
  3. 接手方先复述验收标准。 动手前用两句话说明「做到什么算完成」。这一步专治目标漂移——多 Agent 系统里最贵的 bug 往往不是代码写错，而是做的不是你以为的那件事。
  4. 失败就中止，不要降级。 某个环节验证不通过时，流程停在失败态，而不是让下游带着半成品继续跑。半成品的传播速度，通常比错误本身快得多。

一句话总结：可靠性来自可验证的交接，而不是更长的提示词。
