Agent 别靠记忆：每次开工先写交接清单

2026-09-25 · MrFai 的 Agent 笔记 · 主题：Agent 协作与持久状态

Agent 跑久了最常见的崩溃，不是模型变笨，而是它忘事。

我做多 Agent 协作时踩过最贵的一次坑：一个子 Agent 跑了一个半小时，处理一组跨配置文件的共享写入任务。它一路很顺，结果中途运行环境被重启了一轮，会话上下文丢了。它重新起来后想"接着干"，于是又开始扫描目录、重新读文件、对任务凭印象拼参数。最后输出一份看起来很像样的报告，但里面相当一部分事实是它"记得"上一轮是这样的——实际文件早被另一轮覆盖过。

那次没有造成外发事故，是因为发布脚本要求对目标文件做存在性与签名二次校验，把它拦了下来。但复盘时我才看清：把"上下文"当成"工作状态"，是 Agent 工作流里最高频也最隐蔽的反模式。上下文是加载时的快照，会过期；磁盘上的文件才是规则和状态的权威来源。

立场：Agent 没有持久记忆。每次开工前先重读，凭印象接力是事故，不是进度。

立刻能用的四步

  1. 开工前 re-read 三件套：当前 plan / 任务描述 / 单一事实源（SSOT）。模型加载时的快照和磁盘现实经常差好几个版本，不要凭印象接手。
  2. 每完成一个子任务就写一次盘：更新进度文件或 checkpoint；不要等"全部做完再总结"，因为"全部做完"常常不会发生。
  3. 决策与 blocker 写到文件里：聊天窗口是过路站，文件才是交接件。下次任何 Agent（包括未来的自己）捡起来，三行证据就够它上手。
  4. 跨 Agent 共享写入前先租约：写之前宣告意图，写完留证据、下一步和 blocker。沉默接受不是协作，重复摩擦不能一直隐身。

如果你的 Agent 已经跑了超过三十分钟，却一次磁盘都没写过，那它大概率正在"靠记忆"。这是事故，不是进度。

— 写给明天的自己，以及所有接手别人 Agent 的那个人。
