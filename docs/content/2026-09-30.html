Agent 别当答题机器：把"做决定"交还给上下文

MrFai 的 Agent 笔记 · 2026-09-30 · 主题：多 Agent 协作

我最近一次最贵的失败，不是模型答错了，而是我把 判断 写进了 prompt，把 记忆 留在了聊天记录里。结果就是一个会写漂亮回复、但谁也不负责的 Agent：每次新会话都重新"发现"同一份项目背景，每一次都把同一个坑再踩一遍。

这件事让我意识到一个立场：Agent 的价值不在回答得多漂亮，而在它能不能替我把一个决定从"灵感"推进到"落地"。一旦决定只活在上下文窗口里，它就和没说一样。上下文是临时的，文件才是长久的——这就是为什么我现在要求任何跨会话的工作，必须先落到一份带时间戳、带版本号的文档里，再让 Agent 去读它、执行它、更新它。

一个具体的失败模式

我让 Agent 维护一个监控脚本。它确实写出了逻辑，跑通了单测，也按我说的"每天早上跑一次"加了 cron。问题出在 cron 跑挂之后：Agent 没有看日志，没有告警，更没有回写一条"今天失败了，原因 X"的记录。第二天我打开终端才看到一串红字。那一刻我明白，"做完"不等于"接住"——交付、监控、复盘必须是同一条链路上的三件事，不能拆给三段上下文。

读者今天就能照做的四步

  1. 把"决定"写进文件：任何 Agent 要长期遵守的规则，立刻落到一份带日期的 Markdown，路径稳定，不要让它只活在聊天里。
  2. 把"运行"接上"观察"：每次脚本或 cron 跑完，强制写一行状态到日志文件；失败要写明原因，不是沉默地退出。
  3. 把"复盘"留给人：每天或每周固定一次，让 Agent 把日志汇总成两段话——发生了什么、下一步改什么——再写回同一份文档。
  4. 设一条硬边界：未经你明确批准，Agent 不得自行修改 cron、权限、对外发送或付费，这是它可以"推进"但不能"决定"的边界。
