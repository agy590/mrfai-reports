别让 Agent 互相确认：把评审留给最贵的那一次

2026-10-27 · 多 Agent 协作 / 工程实践

做多 Agent 协作之后，我最贵的教训不是模型不够强，而是「互相确认」。

早期流程很顺：规划者写计划，执行者照做，审查者复核。后来我加了保险——执行前让规划者再确认一次计划，通过前让审查者再和执行者对一次口径。出问题时，三方都拿对方的结论当证据：规划者说执行者理解偏了，执行者说计划写清楚了，审查者说两边都确认过。没有人读过原始文件，错误却被三方背书，排查成本翻了好几倍。

真正的分界不是「谁来审」，而是「审什么」。交付物只有结论，评审就只是复读机；交付物带着证据（可复现的命令、真实输出、具体文件路径），评审才可能变成核对。

现在我的做法很简单：状态写进文件，动手前先重读盘，不靠记忆和上一轮的口头结论；同一路径同时只允许一个写入者；审查者只判定通过或不通过，修复回到执行者手里；收尾时逐条对照验收标准，缺证据的地方直接标成阻塞项，宁可留一个明确的「未验证」，也不让它混进已完成的部分。

共享一套状态，多 Agent 才不是多线程瞎跑；否则只是把一个人的混乱复制成三份。

  1. 交付证据，不交付结论。每次产出都带可复现命令、真实输出片段和具体文件路径，审查者只核对这些，不接受转述。
  2. 状态写进文件。决定、阻塞项、下一步落到磁盘，谁动手前先重读最新版本，不靠记忆。
  3. 写入先领租约，评审只判定不修复。同一任务或路径同时只允许一个写入者；审查者给出「通过 / 不通过」，修复交回执行者。
  4. 收尾逐条对照验收标准。缺证据就标成阻塞项，宁可留下一个显式的「未验证」，也别把它混进已完成。
