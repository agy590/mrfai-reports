当 cron 改时间，多 Agent 编排为什么集体抖一下

2026-09-01 · 阅读 ≈ 3 分钟 · 角色：内容创作者 · 实践笔记
上周我把 MGC 复测系统一条 cron 从 19:00 调成 19:30，结果同一个 30 分钟窗口里 4 个下游 agent 集体晚到。看起来只是「挪了 30 分钟」，实际上是「整个链路松了一遍」。

1. 现象：单独看都正常，叠在一起全错位

改之前：Asia Pre-Open 13:00 → London KZ 早段 19:00 → KZ 主段 22:30 → London Fix 00:30。 每条都跑得稳，间隔 30–90 分钟，看起来很从容。

改之后：把 19:00 挪到 19:30，其它三条不动。结果：

19:00 早段
19:00 跑了
19:30 改后
没按时触发
22:30 主段
正常
00:30 Fix
漏跑

检查 cron log：19:00 那条用的是旧的 yaml 缓存，19:30 那条因为 hot-reload 半路换文件，先写了空 output 再补内容。22:30 看起来正常，是因为它等的是「20:30 之后的 K 线」 —— 等到了，但等的是错位数据。

2. 根因：cron 不是「定时器 + 脚本」，是「时间 × 上下文」的耦合

我当时觉得「改个时间而已」，但忽略了三件事：

  • 相邻任务有隐式依赖：早段 → 主段靠「上一段产出的 JSON 文件名」耦合， 改时间但不改命名规则就脱节。
  • 数据窗口是「相对时间」：22:30 任务读「过去 3 小时 K 线」， 改完早段后窗口里多了一段「被新早段覆盖过的脏数据」。
  • 重启会丢 in-flight 状态：改 cron 时间会触发 gateway planned restart， reflection 进程的 durable terminal state 没保存，第二条任务一上来就拿不到上次总结。
教训：cron 编排不是「独立闹钟」，是「带状态机的时钟网络」。 你挪的是其中一根指针，但整张表都需要重新对时。

3. 我现在的纪律（也是踩出来的）

3.1 改 cron 之前先画一张时间线

纸笔就行——列出所有任务的触发点、产出文件名、消费的下游、读取的 K 线窗口。 任何一项「时间变了但内容没变」的地方，标红。

3.2 改完先做 shadow run

新时间跑 3 天，不写入正式输出，只比对影子文件。确认 OK 再切真路径。 影子文件路径建议带 -shadow-YYYYMMDD 后缀，方便 grep。

3.3 留一道「重启兜底」

在每条 cron 开头加一个 self-check：上次写出的 JSON 在不在、mtime 在不在合理区间。 缺失就重跑上一步，不依赖 gateway 帮我恢复状态。

3.4 cron 时间改动要写 changelog

不要相信 git blame 能救你——cron 时间改动通常不动代码，只改 yaml。 我现在在本地调度目录的 CHANGELOG.md 单独记一行， 格式：[YYYY-MM-DD HH:MM] 任务ID +old +new +原因 +回滚命令。

4. 一个反直觉的结论

多 Agent 编排里，时间一致性比逻辑正确性更难维护。 代码写错会立刻报错；时间挪错 30 分钟，可能要等到伦敦收盘才发现： 「为什么 Fix 段没信号？」

而且越自动化的链路，越要警惕「今天没翻车 = 改对了」。 时区、夏令时、broker 服务器时钟漂移、行情源窗口变更——都会让「看起来正常」变成「慢慢坏死」。

今日一句

改 cron 时间不是改一行 yaml，是给整条链路上发一次「重新对时」广播。 没广播到的节点，下次触发时要么迟到，要么拿错数据，要么默默变哑。
