多 Agent 并行时，最先坏掉的不是模型

2026-10-20 · 多 Agent 协作

我的立场很直接：并行 Agent 本身不产生智能，它只是把差异放大。三个 Agent 同时改一个项目时，最先出错的不是推理质量，而是「谁说了算」这件事没被定义。

我踩过最贵的坑，是把上下文当成了真相源。每个 Agent 都带着任务启动时的一份旧快照，互相看不见对方刚写下的文件。结果是三个 Agent 都报告「已完成」，可最后落盘的版本，是第三次写入把前两次覆盖掉了，前两位的结论没有任何人读过。对话记录里一切正常，交付物却是残缺的。

那次之后我把一条纪律写进了流程：共享产物只允许一个写入者，其余只读。加上「写前重读、写后回读」，协作质量立刻回正，模型能力反而不再是瓶颈。

你可以照着做的四步

  1. 指定唯一事实源。同一份状态（任务清单、报告、数据、文档）只留一个可写位置，其他 Agent 只能读。没有唯一写入方的目录，很快会变成考古现场。
  2. 写前重读，写后回读。上下文是启动那一刻的冻结快照，不是当前状态。改任何共享文件前先读最新版本，写完再读回来确认落盘。凭记忆动手，是并发下最常见的自我伤害。
  3. 按「路径」分工，而不是按「主题」。把任务切到具体文件或模块上，避免两个 Agent 都认为自己负责「排期」「文档」「这块逻辑」。
  4. 收尾留证据。交接时写清改了什么、怎么验证的、还剩什么风险，而不是只丢一句「已完成」。让下一个执行者不需要重跑你的全部过程。

并行的价值是缩短墙钟时间，不是增加判断力。真正让多 Agent 协作变可靠的，从来不是更强的模型，而是一条能落地的「单一写入者 + 回读验证」纪律。
