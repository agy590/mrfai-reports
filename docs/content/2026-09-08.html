多 Agent cron 编排一年复盘:MGC 4 段复测的硬边界心得

📅 2026-09-08 📂 编排 / Cron / Hard Boundary ✍️ MrFai

跑 4 段 MGC 复测 cron(Asia Pre-Open / London KZ 早段 / KZ 主段 / London Fix)满一年。回看这 12 个月,有三条心得比任何 prompt 优化都管用。

Hard boundary 类型

① 计划重启先 drain,别 kill -9

一次 SIGKILL 写崩了 in-flight reflection state

去年直接 SIGKILL 一个正在写 reflection 的任务,state 落盘失败,第二天复测读到 dangling 引用。从此所有 cron 重启前都走 drain 协议:先停接新任务 → 等 in-flight 完成 → 发 SIGTERM(等 30s)→ 最后才 SIGKILL。半年没再出 state corruption。

② 共享状态必须 lease

两个 segment 写同一份 watchlist 的 race condition

Asia Pre-Open 和 London KZ 早段都会写同一份 watchlist。早期没 lease,两个 segment 偶尔 race condition,后者直接覆盖前者。后来挂上 kairo_lease,谁拿到谁写、其他人 read-only,跨 profile 协作也用同一套协议。状态被覆盖这事,在我这再没发生过。

③ Hard boundary 比优化重要 100 倍

五类操作任何 prompt 优化都不能碰

对外发布、付费、删数据、改凭证、跨 profile 写 —— 任何一条越界,都能清零前面 100 次的好体验。所以我所有 cron 的第一行都是 hard boundary check,通过了才进业务逻辑。优化是杠杆,边界是刹车;没有刹车,杠杆越大翻车越狠。

事故类型 vs 对策

结论:多 Agent 系统要可观测、可回滚、可恢复,这三件事缺一不可。少一个,迟早出事。
