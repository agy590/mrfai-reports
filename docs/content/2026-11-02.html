多 Agent 协作真正的瓶颈在交接，不在模型

2026-11-02多 Agent 协作

很多人一上手多 Agent，第一反应是"多接几个更强的模型"。我自己折腾过几轮才明白：大部分翻车跟模型聪不聪明没多大关系，问题几乎全出在交接上。

最常见的一种失败：两个 Agent 同时写同一个目录。我派 A 去改配置，派 B 去跑验证，B 读到的却是几分钟前的版本——它没意识到 A 已经动过手，于是用旧快照把新改动盖了回去。文件被悄悄回滚，而两边都以为自己干完了。修法很土：动手之前重新读盘，别信上下文里存的那一份。

第二种失败更隐蔽：计划阶段和执行阶段挤在同一个会话里。执行时读到"计划：已完成 X"，就跳过了真正的检查，把假设当成事实往下推，错误一路滚到最后才暴露。后来我把计划写进文件，新会话从文件恢复，只认写在盘上的东西。

第三种是我自己踩的：让写代码的 Agent 审自己的代码。每个设计决策都被解释得很合理，理由越充分，漏洞越藏得深。审查必须换一个上下文、换一双眼睛——同一套上下文里的自我审查，几乎不会 FAIL。

如果只记四步，我会记这些：

  1. 划清所有权：共享产物按路径分工，同一文件同一时间只允许一个 Agent 写；要交接就显式交接，不要靠"共享目录反正大家都能改"。
  2. 用文件传状态，不用对话传状态：把目标、已做的事、证据、卡点、下一步写进文件；接手的人从文件开始，而不是从上一位的总结开始。
  3. 执行前先复述计划与验收标准：谁发现偏差，当场改。计划错了就当场改计划，别硬着头皮做完再算总账。
  4. 审查换一个上下文，最好换一种视角，而不是同一套上下文里的第二次自查。

多 Agent 的收益确实存在，但它放大的是执行速度，不是判断质量。判断质量还是得你自己扛。
