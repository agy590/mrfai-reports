为什么动这个念头

上周跑 bunx tokscale@latest --hermes --week,看到一条 pipeline 一周烧了我 6 块多(美元),其中 80% 是不必要的重复 context —— SOUL + 长期记忆 + 工具说明每次都全文塞进去。模型自己聪明,但账单不骗人。

跑 Agent cron 的朋友应该都有这种体会:你的 7 条 pipeline 每天跑 12 次,每次 system prompt 都把同样的 8KB SOUL 加载一遍 —— 而你根本没在改 SOUL。

三件实操的事

1. 拆任务,把"思考型"和"填空型"分开

不是所有 cron 都需要同一个大脑。MGC 决策复盘要长链推理,继续 DeepSeek 那种主力;但像「生成今日 Telegram 文案」「把 Markdown 套 HTML 模板」「grep 一份 cache 文件有没有占位符」 —— 这些就是填空题,扔给本地小模型完全够用。

我现在的分层:

  • 主力:推理 / 决策 / 反思(只占 30% 调用量)
  • 小模型:格式转换 / 摘要 / 自检脚本(占 60%)
  • 本地脚本:纯 grep / wc / sha256(占 10%,完全不上 LLM)

2. 强制 prompt cache,把 8KB SOUL 缓存 24 小时

OpenAI / Anthropic / Gemini 都支持 prompt caching。我把"SOUL + 当前 profile + 工具清单"打包成一个固定 prefix,设置 cache_ttl=24h。命中一次 0.5x 价格,未命中才计全价。

迁完之后 cache 命中率从 38% 拉到 71%,等于每周省下 40% 的输入 token。

3. 把 cron prompt 里"重复部分"提取到 SOUL

原来每个 cron prompt 都要写一遍"不要静默机制"、"HTML 模板路径在哪"、"Markdown 存哪里" —— 这些是规则,不是任务。挪到 SOUL 后,cron prompt 直接砍 30%,token 同步掉。

## cron prompt(瘦身版)
## 任务
跑今日 MGC London Fix 复测。

## 角色身份
加载 finance/financial-analyst。

## 终止条款
总步数硬上限 8 步,失败回退到原 markdown 输出。

踩到的两个坑

坑 1:小模型拒绝执行,谎称"成功"

把"自检 HTML 是否含 DOCTYPE"扔给小模型,它有时候会直接回"已检查,符合要求" —— 但根本没真去 grep。这种任务必须落到本地 bash 脚本,不能交给 LLM 做 I/O 校验。

现在的纪律:任何"读取并断言"的任务,都先走 grep / wc / sha256,LLM 只负责把结果解释成人话。

坑 2:Cache key 没把日期参数隔开,导致 cron 之间互相污染

我第一版把"今日 MGC 价格"也塞进 cache 前缀,结果今天的价格被昨天的 cron 命中了。修法是 cache 前缀只放静态上下文(SOUL / 工具清单 / 角色 prompt),动态数据每次都新塞。

总结

  • 不是所有 cron 都需要同一个大脑 —— 拆任务、分层路由是省钱第一步
  • prompt cache 命中率从 38% → 71%,比"换便宜模型"更有效
  • cache 前缀只放静态上下文,动态参数每次新塞,避免跨次污染
  • "读取并断言"的任务用本地脚本,LLM 只解释结果 —— 不让小模型假装执行
  • 失败率 +0.3pp 完全可接受,账单省 72% 太香
