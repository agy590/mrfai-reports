多 Agent 协作里最贵的不是模型，是状态漂移

2026-10-22·多 Agent 协作 / 工程实践

我做过一次并行改配置的尝试：三个 agent 各自拿到一份旧快照，分别提出"改进"，然后同时写回同一个文件。结果不是三份改动合并成一份，而是三份互相覆盖，最后留下的版本里混着两个从未同时存在过的假设。

从那以后我只信一条原则：状态比推理更贵。多 agent 系统的瓶颈很少是模型不够聪明，而是没有一个明确的"事实在哪里"。只要真相可以同时存在于三个地方，任何校验都会在冲突中失效。

更隐蔽的失败是"验证幻觉"：agent 写完代码后自己跑一遍测试、看一眼输出，就报告完成。但它验证的往往是自己上一步的中间状态，而不是最终落盘的那份东西。子 agent 报告 PASS 也不构成独立证据——它和执行者共享同一套假设。真正可靠的做法只有一条：关掉上下文，重新从磁盘读一遍最终产物，再判断。

所以我把规则收得很紧：共享产物只有一个写入者；每次改写都留下可追溯的版本记录；任务中断时必须写清证据、决定、阻塞项和下一步，而不是让下一轮从零开始猜。

今天就能照做的 4 步

  1. 先定事实源。动手前写下一个唯一可信的产物位置，其余 agent 只读它，不各持一份副本。
  2. 划清写入归属。谁负责哪个文件要显式声明；遇到冲突排队处理，不要靠合并掩盖。
  3. 独立回读验收。验收必须由没写过这段内容的 agent 从磁盘重读最终产物，而不是采信执行者的自述。
  4. 留痕不压缩。失败和中断也要写下证据、决定、阻塞项和下一步，别让下一轮靠上下文猜。
