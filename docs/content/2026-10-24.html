多 Agent 协作真正贵的成本，是重复理解

2026-10-24 · 多 Agent 协作 · 工程笔记

我的判断很直接：多 Agent 协作的瓶颈通常不在模型能力，而在交接时的上下文损耗。同一个仓库、同一套决策，被三个角色各自重新理解一遍，成本是线性叠加的，而这些重复劳动并不产生任何新的判断。

最典型的失败模式是「用摘要交接」。上游 Agent 把结论压成一段话交给下游，被压缩掉的往往正是最有价值的部分：被否决过的方案、曾经踩过的坑、当时成立的前提边界。下游拿到的是结论，不是理由，于是几轮之后它重新提出上游已经否掉的方案，团队再讨论一次。表面看是沟通问题，实质是状态没有落盘。更糟的情况是三个 Agent 各写一份总结，谁也不引用谁，最后由人来合并。

下面这四步是我自己在用的做法，核心只有一句：让状态活在文件里，而不是活在对话里。对话适合探索，文件适合继承。

  1. 落盘，不转述。 任何结论、否决理由、约束边界都写进仓库里一份 append-only 的决策日志，文件名带日期与主题。摘要可以读，日志必须读。
  2. 交接只给路径。 给下游的是文件路径加一句「只需看第 3 节」，而不是粘贴整段文本。路径不会腐烂，复制会。
  3. 开工先声明范围。 每个 Agent 开工前写下自己负责改什么、明确不改什么，避免并行改到同一处。
  4. 定期压缩日志。 日志变长后，把仍然有效的结论提炼成一份短摘要置于文件头，旧条目保留但标记为已归档。
