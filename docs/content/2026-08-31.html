多 Agent 编排

同时跑 4 个 cron Agent 之后，我才懂「durable state」是什么意思

一次被 SIGTERM 反复教育出来的教训——Agent 任务的「完成」和「持久化」从来都不是同一件事。

2026-08-31 MrFai 的 Agent 笔记 实操经验 · 6 分钟

症状：reflection 步骤天天丢一半

我现在常驻 4 个 Hermes cron：MGC 期货复测、AI Radar 周报、Agent 笔记日更、NQ FVG 扫描。前 3 个跑得稳，第 4 个的 reflection 步骤天天掉链子。

具体表现：每次 gateway 计划重启后，最后一个写 reflection 的 Agent 进程被 SIGTERM 杀掉，Markdown 写了一半就停在那里。下一次 run 起来，读不到上次结论，signal 又从头跑一遍。一周下来，复测系统里至少有 3 天是在「基于昨天的残篇做决策」。

4

根因：把「terminal」当成「durable」

我的 mental model 一直是：Agent 跑完了 = 状态持久化了。但实际是——gateway 重启时只持久化 agentmemory 的 checkpoint，不持久化文件系统的半成品。reflection 又是 reflection.md 单文件直写，进程被杀就剩半篇。

修法：拆成 3 步 + atomic write

把 reflection 拆成显式三步，每步都是 checkpoint：

# crontab-style reflection flow (伪代码)
- step 1: commit_checkpoint
    → 写 agentmemory checkpoint（含 session id、key facts）
- step 2: write_md_atomic
    → 先写 reflection.md.tmp，再 rename 到 reflection.md
- step 3: commit_done
    → checkpoint 标记 done，下次 run 跳过

关键就在第二步的 atomic rename：哪怕被 SIGTERM 杀掉，要么完全没写，要么写完了，下一次 run 一定能读到完整版。配合 step 1 的 checkpoint，重启衔接就是确定的。

核心教训：Agent 任务的「完成」和「持久化」是两件事。文件系统的 atomic write 是底线，agentmemory 的 checkpoint 是加分项，但都不是默认行为——必须显式做。

顺手整理的 checklist

  • 任何写盘步骤都用 tmp + rename，不要直接覆盖
  • agentmemory checkpoint 在「开始写文件前」就 commit，不要写完再 commit
  • 下次 run 启动时先读 checkpoint 状态，不要凭"上次应该跑完了"假设
  • gateway 计划重启前，先 drain cron queue，再 kill，不要强杀

小结

多 Agent 编排最难的不是写 Agent，而是让 Agent 在「被打断」这件事上不出错。SIGTERM、OOM、network blip、disk full——这些都是常态，把它们当边界条件而不是异常情况去设计，cron 才能 7×24 真的稳。
