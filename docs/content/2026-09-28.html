多 Agent 协作的隐形雷：共享状态没有 SSOT

MrFai 的 Agent 笔记 · 2026-09-28

跑多 Agent 协作最常见的崩盘方式，不是模型出错，也不是 prompt 写得烂，而是几个 agent 同时改共享文件、改配置、改 cron 的运行计划。每个人都说"我记得是 X"，最后线上跑的是 Z。

我自己就踩过：a 进程基于昨天的内存快照把注册表写成"启用"，b 进程同一时刻根据磁盘实际状态判断是"禁用"，两者各自 review 都通过，线上却跑出谁都没见过的混合行为。复盘下来，根因只有一个——没有把"哪个文件、哪个时间点、谁授权改"当成一等公民来管。

更糟的是，agent 的"记忆"会骗人。上下文只是加载时的快照，会过期；下次重启、换 session、压缩记忆之后，没人能复现"上周三为什么把那行注释掉了"。口头约定和聊天记录不是交付物，磁盘上的文件才算。

立场

共享状态必须显式版本化。Single agent 的"我记得"不能作为权威；磁盘上是真相，旁证、磁盘记录才允许落地。

读者能照做的四步

  1. 给每类共享产物指派单一权威文件（SSOT），其他位置只放副本或派生态。Cron 配置、运行计划、agent 注册表都是典型候选。
  2. 任何修改先读盘、再改、再写回；改完落 sidecar 或 commit，明确记录"谁、什么时候、为什么"。
  3. 跨 agent 交接前必须 checkpoint：把当前状态、决定、blocker、下一步写成可恢复的产物，而不是"下一棒接着干"。
  4. 每条 cron、每个常驻进程跑前自检一次：磁盘实际状态 vs 内存快照，不一致就拒绝启动并报警。

多 Agent 协作的真正杠杆，不是让每个 agent 更聪明，而是让它们的分歧无处藏身。
