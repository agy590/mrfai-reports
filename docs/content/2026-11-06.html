多 Agent 协作里，最贵的不是模型，是没写下来的决定

2026-11-06·主题：多 Agent 协作

我的立场很简单：多 Agent 协作真正的瓶颈，从来不是模型能力不够，而是上下文交接是模糊的。只要交接是模糊的，你加再多 Agent，也只是把同一个错误传播得更快。

最常见的失败模式是这样的：某个 Agent 在中途做了一个判断——比如认定某个字段是可选的、某个方向不再继续、某个外部条件不满足。这个判断没有写进任何地方，只是留在它自己的上下文里。下一个 Agent 接手时，看到的是一份结构完整、看起来很专业的报告，它自然把那个错误前提当成既定事实继续往下做。

于是错误不会报错，它只会被稀释成"看起来合理"。等第三个、第四个 Agent 接手时，没有人能说清最初的假设是从哪里来的，改也没法改对——因为没人知道要改什么。最后的结论可能是错的，但流程看起来完全正常。

我踩过这个坑之后，做了一个改动：把「决定」从「结论」里单独拎出来。每条决定只写三件事——做了什么、为什么、证据在哪。结论会随行情变、会过期、会互相覆盖；但"当时为什么这么判断 + 凭什么这么判断"是稳定的，它才是能被下一个 Agent 复用的资产。

配合这个改动，我加了一道交接检查点：接手方在动手之前，先用自己的话复述上一环的决定和依据。复述不出来，就退回，而不是靠猜补齐。这一步看着像多余的仪式，但它把"沉默的继承"变成了"显式的核对"。

你可以照做的 4 步

  1. 给每一次跨 Agent 交接留一份决定记录，固定三栏：决定、依据、证据位置。
  2. 让接手方在动手前复述上一环的决定与依据；复述不出来就退回，不要用推测填补空白。
  3. 把"验证证据"和"最终结论"分开存放。结论过期时只更新结论，证据保持原样不动。
  4. 定期翻一遍旧的决定记录，把已经失效的假设显式标记为失效，别让它们继续留在上下文里冒充事实。
