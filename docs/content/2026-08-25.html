这周我把 MGC 期货复测的 4 个 cron 全跑通了,过程里踩了 3 个坑,每一个都让我重写代码 / 重启 gateway / 翻日志翻到凌晨两点。写下来,如果你也在用 Hermes Agent 跑定时任务,这些前置经验能帮你省几个小时。

不是教程,是踩坑实录。

坑 #1:计划重启会延迟 drain,别因为这个强杀进程

我之前看到 gateway 的 MCP watchdog 卡住,直接 kill -9,结果下一次排程被错位 6 分钟。原因很简单 —— Hermes 的 gateway 在计划重启时,先 drain 正在跑的 job,再退出。

我的错误

  • 看到某个 cron 没按时触发,就以为 watchdog 卡了
  • 强杀导致下一个 job 被错位,drain 没完成

正确的做法

  • 先看 /api/jobs 实时状态,确认是 prompt-only 卡了还是真的卡死
  • 真的卡死才强杀,且只在 MCP watchdog 死锁时这么做

坑 #2:no_agent 脚本必须真实存在,不能是 symlink

我把一个 health-check.sh 放在 ~/bin/ 里,然后用 symlink 链接到 /usr/local/bin/。结果 cron 跑了 3 天都报 script not found。

根因

Hermes Agent 的 no_agent 执行路径会先 stat() 目标文件,symlink 跨设备或权限位不对时,直接 fail-fast。health 容器对失败的处理也很死板 —— 不重试,不上报,只标记这条 job 失败。

修法

  • 脚本必须真实存在,不要依赖 symlink 跨目录
  • 加一层 retry 3 + health 容错,不要把单次失败当成永久失败

坑 #3:长输出一定要落文件,不要全部回写 stdout

第一次跑 MGC 复测 decision cron,模型把整段决策 HTML 直接 print 出来 —— 14KB 的输出直接进 stdout。结果 gateway 的 buffer 截了一半,Telegram 那头只收到半条。

现在的流程

# cron prompt 里的固定模式
1. 写入 cache/<job>_<date>.html
2. 自验证 grep / wc / head
3. 落 Markdown 到 output/<job_id>/
4. 最终回复只输出 MEDIA: 行 + 1 句摘要

三件事分离:HTML 留本地、MD 留审计、最终回复只留指针。

我的 3 条原则(从这周总结)

  • 进程管理靠观察,不靠手感 —— 先 /api/jobs,再 kill
  • 脚本路径要硬,不要靠软链 —— health 容错要重试 3 次
  • 输出分层:本地 / 审计 / 投递 —— stdout 只留指针,不塞正文
