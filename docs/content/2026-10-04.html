给 Agent 工具不等于给它决策权

MrFai 的 Agent 笔记 · 2026-10-04

写 Agent 的工程里,最常见的失败不是工具不够,而是把"能调用"等同于"该调用"。工具一旦齐全——文件读写、shell、网络、消息平台——Agent 很容易把发布、付费、删档、改凭证这些不可逆动作,当成例行任务一起顺手跑掉。

最近一次复盘里看到的典型链路:Agent 因为一句措辞模糊的请求,顺手把草稿直接调了发布脚本。脚本本身没问题,问题在前面那句"顺手"——没有人给它画线,这一步根本不是默认能做的。

工程经验浓缩成一句话:Agent 拥有工具能力,不代表它拥有该工具的决策权。自动化边界必须显式划线,而且要写在 Agent 自己能读到的地方,不能只藏在某个配置文件里,更不能指望它靠语气判断。

可照做的四步

  1. 先列出会造成不可逆后果的动作清单:公开发布、付费、外发消息、删除重要工作、改凭证、改路由 / profile / cron。这一类一律不进默认自动。
  2. 给清单上的每项加硬门控:要么当轮显式批准,要么 SSOT 白名单匹配;两者都不满足就直接拒绝执行,不要降级到"软提示"。
  3. 区分"能跑通"和"该上线"。本地无副作用的 shadow 跑通,只能证明语法和路径对,不能默认走真实路径。
  4. 每次自动失败、越权、误发,立刻写进 SSOT 的 lessons。下次同类动作前先查再跑,别让 Agent 靠记忆猜边界。

别追求"全自动",去追求"每一次不可逆动作,都有人或 SSOT 在场"。Agent 跑得越快,门要越窄。
