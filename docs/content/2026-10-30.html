并行 Agent 真正的成本是上下文，不是 token

2026-10-30 · 主题：多 Agent 协作

我不认为多 Agent 的价值在于「多」。一个 Agent 顺序做完，通常比三个 Agent 并行更快也更可控。真正的收益只在两种情况下出现：任务能切成互不重叠的边界，或者需要独立视角互相证伪。其余时候，多 Agent 只是把同一份上下文复制三份，让冲突成本翻倍。

最常见的翻车原因不是模型笨，是状态漂移。典型的场面是三个 Agent 同时跑，各自的会话里都留了一份「当前进度」：一个已经改完接口，另一个还在按旧接口写胶水层，第三个基于过期假设在补测试。谁都没错，三份描述却互相矛盾，合并时才发现整个假设都建在旧接口上。更隐蔽的一种是交接只留叙述、不留证据——「我做了什么」会漂移，diff 和测试结果不会。

要真的用好并行，可以照这四步走：

  1. 先切边界再开工。把任务切到文件或模块级所有权，每个 Agent 只写自己那块，跨边界的改动先合并再继续。
  2. 只留一份事实源。状态、结论、证据写在一处，其他 Agent 只读不复制；多份副本就意味着多份真相。
  3. 交接带证据不带叙述。写清楚改了什么、怎么验证、结果在哪，让接手的人能复现而不是相信。
  4. 指定收敛责任人。合并和最终判断要有唯一出口，否则只是把冲突推迟到最后一刻。

如果你的任务不满足前面两个收益条件，就别并行。能顺序做完的事，顺序做更省心。
