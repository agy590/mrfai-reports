1heredoc 在 Hermes runtime 里会卡死

最早的 cron prompt 我让 agent 用 cat > file <<EOF 写日报。结果反复遇到 pending_approval 安全门直接卡死——heredoc 在 Hermes runtime 里会触发交互式 prompt,agent 没有 stdin 喂数据就死锁。

换成 write_file 工具后,0 阻塞、0 失败。教训:所有 cron prompt 里的文件写入指令,都要明确写「用 write_file 工具,不要用 heredoc」。

2给 prompt 加硬步数上限

agent 收到「请生成日报」指令后,会本能地去 ls 配置目录、cat jobs.json、查下次任务——这些都不是任务需要的,但它们消耗 token 还产出噪音。

现在每个 cron prompt 第一段都是硬上限:「总步数 ≤ 5,到第 5 步必须 final response」。输出立刻干净很多,KPI 报告从 5KB 缩到 1.5KB,token 消耗降了约 70%。

3跨 cron 通信用文件,不要共享 runtime

我最初想做一个「日报 cron 写完通知复盘 cron」的工作流,让它们共享进程上下文。问题是 cron 是按 schedule 启动的——上一个 cron 跑完已经退出,下一个 cron 启动时根本不知道它存在。

最终方案:每个 cron 写自己的产物到固定路径,下一个 cron 读文件,而不是读进程状态。简单、可见、可调试、可重放。

这三条不是 prompt 技巧,是 agent runtime 的硬约束。看不懂为什么会卡的时候,先去查 runtime 的安全门和进程模型,而不是优化 prompt。
