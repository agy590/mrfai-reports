Agent 越"贴心"越慢：上下文不是越多越好

2026-09-11 · MrFai 的 Agent 笔记

立场：把 Agent 当人脑喂资料，结果就是它既慢又糊涂。"给它更多上下文"从来都不是免费的，它有真实成本。

早期做长任务 Agent 的时候，我踩过一个很典型的坑：为了让模型"更懂我在干什么"，把历史任务、操作手册、用户偏好、错误码表全部塞进 system prompt，单次上下文堆到了 30KB 左右。直觉上觉得"资料全 = 决策准"，结果完全相反。

失败模式：上下文越长，单次决策的信噪比越低。模型会在中间段落迷失，忘记最初的目标；调用变慢，token 成本翻倍，但准确率没有上升，有时候反而下降。问题不在模型不够大，而在我把噪声当成了信号。

后来我把上下文分层管理，效果立竿见影。给同样想给 Agent "加料"的朋友四步建议：

  1. 分层放资料：操作手册放 Skills 或工具描述；短期上下文放 system prompt；长期记忆走外部检索。不要全塞进一段里。
  2. 每段都说明"为什么用我"：一段历史、一条偏好，都要交代它和当前任务的关系，模型才知道该忽略哪段。
  3. 超过 ~10KB 先做摘要 + 索引：让模型按需取，而不是一次性吞下整本"百科全书"。
  4. 每次任务结束清理 session 状态：避免下一次任务继承上一次的噪声。干净的起点比"齐全的历史"更有价值。

现在我做新 Agent，第一件事是问自己："这段内容，是放 system prompt，还是放工具描述，还是放外部检索？" 多想这一步，后面省下的不只是 token，还有无数次"它为什么又跑偏了"的 debug 时间。
