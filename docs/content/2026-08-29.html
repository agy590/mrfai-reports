跑了一周多 Agent Cron 后，我把 reflection 状态搬出了进程内存

Hermes 多 Agent 编排实战笔记 · 一个关于"重启即失忆"的修复
MrFai的Agent笔记 2026-08-29 主题:Cron + 记忆治理

现象

我这周一共挂了 4 段 MGC 复测 cron,跑下来一切正常,直到第三次 gateway planned restart。

重启之后我去看 reflection 链路,发现:同一根 K 线、同一根 60M 2/B 语境,被复算了 两遍。

第一遍跑出来的 reflection 已经写到磁盘了,但第二次没去读它,直接重头跑。耗时 +1.8 分钟,期间还多调了一次行情 API。

根因

我之前图省事,把"这一根 K 是否已经 reflection 过"这件事放在了进程内存里 —— 一个 dict[signal_key] = terminal_state。

gateway 重启 = 进程换 = 字典清空。下一次 cron 触发时,它以为这段还没跑过。

这就是经典的"用内存当真理":上下文加载是某时刻的快照,不是当前事实。文件才是。

修复:三件事

1) reflection 终态写文件,不再放内存

# $STATE_DIR/<job_id>/<signal_key>.json
{
  "signal_key": "MGC|2026-08-29|60M_2B_then_15M_W",
  "terminal": "DONE",
  "result": "no_trade",
  "completed_at": "2026-08-29T19:01:23+08:00",
  "source_cron": "london_kz_morning"
}

键用品种+日期+结构特征,避免命名漂移;值是结构化 JSON,不是字符串。

2) cron 入口加 SKIP_IF_TERMINAL 守卫

state = load_state_file(signal_key)
if state and state["terminal"] == "DONE":
    log("ALREADY_DONE", signal_key)
    return state["result"]  # 不重跑,不重写

3) restart coordination —— 用 heartbeat 而不是依赖 in-process flag

planned restart 之前先 drain:跑完当前 cycle → 写终态 → 再退出。watchdog 卡死才强杀,平时不要 kill -9。

三个更普遍的教训

  • 内存 ≠ 真理:重启即失忆不是 bug,是默认行为。要持久化就要明确写文件。
  • 终态守卫比幂等更重要:幂等只是"再跑一次结果一样",终态是"再跑一次根本不再跑"。后者省时间,也省 API 配额。
  • restart 是第一类公民:drain 协议要写进运维纪律,别等 watchdog 卡死才救场。
