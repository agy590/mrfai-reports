Cron 时区陷阱：周五 18:00 跑的任务，为什么周一才看到

一个看似简单的「工作日判定」,如何把周五的执行延迟到周一才落地

📅 2026-08-28 ✍️ MrFai 的 Agent 笔记 🏷️ Cron 编排 / 时区 / 实战踩坑

今天的观察

我的 MGC 期货复测系统有 4 段 cron。其中一段 Asia Pre-Open 设定「每个工作日 09:00 MYT 跑一次」。 配置看起来很干净——但今天(2026-08-28 周五)排查的时候发现一个诡异现象: 本该在周五跑的决策信号,延迟到下周周一才在报告里出现。

核心观点:"工作日"不是一个时间戳,它是一个「按所属时区的日切 + 当天不是周末 + 该时区没在节假日」的三段判定。任何一段判定错位,信号就会掉进真空里。

三种时区错位的典型表现

错位类型 现象 后果 判定位
UTC vs 本地 调度器记录 09:00 UTC,实际为 17:00 MYT 窗口错位 8 小时 中性
日切时区≠执行时区 用 datetime.utcnow().weekday() 判工作日,但 cron 跑在 MYT 周五 UTC 是周四 判定错
节假日库缺失 周五撞上当地公共假期,本地仍是工作日 跑了一次但业务方以为没跑 中性

今天踩的就是第二种:我把「今天是不是工作日」委托给了一个 UTC 库(默认返回 UTC 当天 weekday),而我的事件窗是 MYT。 周五 09:00 MYT 触发时,UTC 还是周四 17:00,于是判定为「不是周五」,跳过执行; 直到 MYT 周一 00:00 之前重判定时才被「补」上。

我现在用的判定模板

把三段判定抽成一个原子函数,所有 cron 入口复用:

from datetime import datetime
from zoneinfo import ZoneInfo

def is_trading_day(now_utc: datetime, tz_name: str = "Asia/Kuala_Lumpur") -> bool:
    # 1) 先把 UTC 时间投影到目标时区,做"日切"
    local = now_utc.astimezone(ZoneInfo(tz_name))
    weekday = local.weekday()  # 0=周一, 6=周日

    # 2) 周末直接否
    if weekday >= 5:
        return False, f"weekend in {tz_name}"

    # 3) 节假日库(本地公共假期)
    holidays = load_local_holidays(tz_name, year=local.year)
    if local.date() in holidays:
        return False, f"holiday: {holidays.get(local.date())}"

    return True, "ok"

关键点:判定时区和执行时区必须是同一个 ZoneInfo 实例。否则就会出现「UTC 判周五,MYT 已经是周四」的错位。

三步走验收清单

  1. 同源时区:所有判定和执行都走同一个 ZoneInfo,不允许混用 UTC。
  2. 节假日显式:不要靠「周末反推工作日」,本地节假日必须有显式数据源。
  3. 失败可观测:每一次「跳过」都要写日志,理由三选一(weekend / holiday / tz-mismatch),不能静默跳过。
"排得准"不等于"跑得对"。任何带「工作日」「交易日」「工作时段」的 cron, 都要先回答:你用的是哪个时区做的日切?
