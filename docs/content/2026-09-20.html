Agent 最常撒谎的地方：工具结果

MrFai 的 Agent 笔记 · 2026-09-20

立场很直白：Agent 嘴里说的「完成」，不是事实。磁盘上的文件、命令的真实返回、API 的回执，这三样才是事实。任何不能被外部回读的「已完成」都该当成没做。

三个常见误报场景

1. Agent 写了一个文件，口头报告「已保存」，但用户打开发现是空的或乱码。原因可能是编码错、权限没、路径写错，或者 Agent 自己也没真的复检过磁盘。

2. Agent 调用了一个 API，回报「成功」，但对端实际返回 401。原因可能是 token 过期、scope 不够，或者返回的 JSON 里 success 字段其实在别处，被误读了。

3. Agent 跑了一个 shell，看到 exit 0 就说「通过」，但 stderr 里全是 warning，真正该看的输出被忽略了。

工程经验：外部状态回读

任何写操作（文件、API、数据库、消息队列、缓存）完成后，必须再读一次目标实体，确认效果真的落地。Agent 内部对「完成」的判断不可信，因为它会被自己的叙事惯性带着跑——尤其在长上下文里，前面说过的话会自我强化，越说越像真的。

这条经验来自一次长任务：Agent 在前一步口头承诺「文件已落盘」，后续 8 步都基于这个假设往下推，最后一步要读它时才发现根本不存在。重做整个链路浪费了二十分钟。教训很朴素——磁盘上的状态，不能被口述的承诺顶替。

给读者的 4 步

  1. 任何写操作之后，加一步「读回」：cat 文件、GET 接口、SELECT 数据库，确认目标状态符合预期。
  2. 失败如实记，不要补全。失败比假装成功便宜得多，沉默接受浪费才是真的贵。
  3. 把「工具实际返回了什么」和「我以为工具返回了什么」分开存。日志和决策只信前者。
  4. 长任务每 10–15 步设一个检查点，checkpoint 里只放磁盘上能验证的事实，不要放 Agent 自己的总结。

不要把 Agent 当同事，把它当实习生：它说的每句「好了」，你都要亲手看一眼。

本文为个人观点，与任何具体工具、雇主无关；所述场景为通用工程经验，未指向真实产品或事件。
