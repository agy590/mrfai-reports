起因

两个 cron 同时改同一个共享配置文件，直接把状态写崩了。复盘后，我把跨 Agent 的写入收敛成下面三件套。这是用真金白银的调试时间换来的三行规则。

1. Lease（租约）

动手前先 kairo_lease 宣告「我现在要改 X」。别人看到有 lease 就不会同时动。这个看似多余的小步骤，省掉了我三天的反复定位——之前那个状态冲突就是因为两个 Agent 都不知道对方也在改。

租约不是锁，它只是声明意图。但只要大家都遵守，光是「可见性」就解决了一半的并发冲突。

2. Checkpoint（断点）

每次交接前写一段：做了什么、决定是什么、下一步是什么、blocker 在哪。比让下一个 agent 自己猜上下文可靠 10 倍。

很多 Agent 协作失败的根因不是协议没设计，而是交接信息太薄——下一个 session 只能从空上下文开始重推理，结果把同一个决定推翻两次。Checkpoint 是把「会话内记忆」蒸馏成「跨会话事实」的唯一靠谱手段。

3. SSOT（单一事实源）

配置只存一处，别在三个地方各存一份然后靠同步脚本糊弄。同步脚本一旦挂掉，沉默漂移就开始了——你不知道哪个副本是真的，直到某个 Agent 拿着错的副本做出错误决策。

SSOT 听起来是老生常谈，但真正难的是「发现」哪一处才是源。我现在用一个固定根目录当锚点，所有写入都必须经过它，没有「快速例外」。

对比：传统同步脚本 vs 三件套

维度 同步脚本 Lease + Checkpoint + SSOT
并发安全 脆弱（无锁） 明确（租约声明）
故障恢复 从零猜上下文 Checkpoint 续跑
状态漂移 高风险 单一来源
上手成本 低 中（但一次性）

教训

多 Agent 的协作成本不在通信，在状态一致性。把状态管好，三个 Agent 和三十个 Agent 没什么区别。真正拖垮系统的从来不是 LLM 不够聪明，而是两个 Agent 对「现在的事实」有不同版本的认知。
