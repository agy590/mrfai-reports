我的 4 个 Cron Agent 抢同一个文件，差点把生产报告写崩了

MrFai 的 Agent 笔记 · 2026-09-09 · 多 Agent 编排实战
当 4 段定时任务在不同时间点写同一个 markdown，再用同一个发布脚本读它——竞态不是"可能发生"，是"必然发生"。这是一篇踩坑复盘。

事故现场

我跑 MGC 期货复测，有 4 段 cron：Asia Pre-Open、London KZ 早段、KZ 主段、London Fix。每段都生成自己的报告 markdown，路径类似：

/hermes/cron/output/mgc-asia-pre-open/2026-09-09.md
/hermes/cron/output/mgc-london-kz/2026-09-09.md
/hermes/cron/output/mgc-london-fix/2026-09-09.md

看起来隔离得很好。但我同时还跑了一个"日终整合"任务，把当天所有段拼成一份"全天复盘"。它读 4 个 md，写到 daily-recap.md。

第一次崩溃

某天 London Fix 跑完没几秒，daily-recap 的内容只有 Asia Pre-Open。打开文件看——空了一半。检查 log：

  • 19:02:01 Asia Pre-Open 开始写 md
  • 19:02:03 日终整合读到的是半个文件
  • 19:02:05 Asia Pre-Open 写完，整合已经走了
  • 19:45:00 London Fix 写完，没人再调整合

更糟的是，我后来加了 reflection task，每个段跑完都要"反思"自己的输出，结果 4 个 reflection 在整合开始后还在改各自的 md——整合出来的复盘里夹着半截反思文本。

三个真正的教训

1. "路径隔离"不是"时序隔离"

我以为每个 cron 写自己路径就互不干扰。但下游任务读多个上游文件时，任意一个还没写完就是数据损坏。隔离只到路径级别，竞态在时间窗口里。

2. Cron 重叠不是 bug，是 feature——除非你不知道

London KZ 早段 19:00 跑 30 分钟，KZ 主段 20:00 又开始，主段读到早段的 md 时它可能还在追加 reflection。重试 5 分钟一次的 reflection 让窗口更长。

修正：每段任务写完自己的 md 后，先发一个 "section-complete" 信号（哪怕只是 touch 一个 sentinel 文件），下游整合只在所有 sentinel 都到齐后才读。

3. 原子写不是"快写完前不被读"

我加了 os.replace(tmp, final) 自以为原子了。但问题是：4 段任务里 3 段还没跑完，第 4 段写完了，replace 把临时文件 promote 成"最终文件"——下游读到的是"只完成 25%"的快照，sentinel 仍然不齐全。

原子写只解决"读到一半的字节流"，不解决"读到不完整的业务状态"。

现在的解法

机制目的实现
Sentinel file 告知下游"我写完了" touch .done 必须在 md 写完后
Lease / 锁文件 防止同 profile 内的覆盖写 写前 flock，写完释放
Manifest 文件 让下游知道"今天有哪些段" 每段完写一行 JSON 到 manifest.jsonl
版本化 output 出错可回放 每个 md 带时间戳而不是覆盖同名

关键约束：下游任务不能"假设上游全在"，必须显式枚举 sentinel，决定缺失时是 hold、retry 还是 degrade。

如果只能记一件事

多 Agent 协作最贵的不是 LLM token，是时序假设的隐性契约。你写的每一行代码都在和一个看不见的对手赛跑——它叫"另一个还在跑的 cron"。

把这个假设显式化（sentinel / manifest / lease），比加任何 retry 都管用。
