把 Agent 当同事，不是当工具

MrFai 的 Agent 笔记 · 2026-09-19

立场：Agent 不是万能助手，更像一个刚入职、记性不好但打字很快的同事。把它当工具用，你会被它的流畅欺骗；把它当同事用，给它明确的边界和验收标准，它才能稳定交付。

一个常见的失败模式

很多人第一次让 Agent 写代码、做研究、跑分析时，会给一句"帮我把这段优化一下"或"调研一下 XX 行业"。Agent 会很快吐出一份看起来完整的结果：结构清晰、有数据有结论。

问题在于：当你对领域不熟时，你没办法分辨这份结果里有几分是真的、几分是它在顺着你的预期填空。这不是 Agent 故意骗你，而是它的默认行为就是"给出听起来合理的回答"。如果不给它可验证的事实来源和明确边界，它就会默认补全。

更糟的是，Agent 的会话上下文是临时的。下次开会它不记得上次说过什么；项目换环境，路径、约定、进度全要重新说明。把每次任务当成一个独立项目来交付，比把它当成一个持续在线的同事，更接近现实。

四个可以照做的步骤

  1. 先写一个 5 行内的"任务合同"：目标、输入、输出格式、禁止事项、验收标准。没有验收标准的任务，等于生产了一堆最后没人复核的中间文件。
  2. 强制要求 Agent 给出可验证的引用：文件路径、命令输出、截图，而不是抽象描述。让它"展示证据"而不是"展示结果"。
  3. 每完成一个子任务就 checkpoint：把当前的结论、决定、阻塞、下一步写下来。中断或交接前先固化，再继续；不固化就交接，等于让下一个人猜。
  4. 3 次未落地就换方向：同一个方案连续三次没被采纳、没被执行、没产生行动，别再换说法，直接告诉使用者："这条路径我没走通，要不要换条路？"沉默接受浪费不是协作。
一句话总结：Agent 能放大你已有的工作方式。如果你的方式是模糊的、不可验证的、靠灵感的，Agent 会把这种模糊以十倍速度放大。先定义合同，再让它动手。
