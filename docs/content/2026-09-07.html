背景：4 段 Cron 同时跑，是怎样一种灾难

过去两周我在 MGC 期货复测系统上挂了一个 4 段 cron：Asia Pre-Open（13:00）、London KZ 早段（19:00）、KZ 主段、London Fix。理论上每段独立，互不打扰。

实际上呢？第三天我就被两件事打了：

  • 空报告率 38% — 4 段里有 1-2 段明明触发了，但 agent 拿不到行情就硬写一份"无数据"占位
  • reflection 状态丢失 — gateway 一做计划重启，上一段刚写完的 signal reflection 直接被吃掉

根因拆解

① 行情上游没到位，agent 就硬上

无 CME 实时 entitlement 时，新浪行情有 5-15 分钟延迟。我之前让 cron 直接调 search_flash，结果行情还没回来，agent 就把"无重大事件"当成事件写进报告。

② reflection 在内存里，没落盘

signal reflection 我原来只写 agent 内存。gateway 计划重启会 drain 任务，内存里的 reflection 跟着进程死。下一次 cron 触发时，agent 以为是"全新一天"，上一段的结论全丢。

③ 4 段没协调，互相抢资源

KZ 主段和 London Fix 间隔只有 3 小时。第二段触发时，第一段的 memory compaction 还没跑完，直接撞上。

修法：三件事

① 上游 gate 写入 cron prompt

在 prompt 里明确"行情延迟 > 8 分钟 = 留白，不要硬写"。给 agent 一个显式的 SKIP 信号，不是 SILENT（那个 token 会被系统拦截）。

② reflection 落盘到固定路径

$HOME/.hermes/cache/mgc-reflection/<date>-<session>.json

cron 启动时先 read 一遍，有就接上；没有就新建。每次写完 flush，不依赖内存。

③ 段间加 lease，避免并发冲突

用 kairo_lease 占住同一 session，第二段检测到 lease 未释放就退后 5 分钟重试。这是 Hermes 现成的工具，不用自己造锁。

样本小（3 天 / 12 次），但趋势明确。gate 写入 + reflection 落盘 + lease 协调，三件事独立，每一件都拉一截曲线。

经验总结

  • cron 不是定时器，是流水线。每段都要有显式的 gate / 状态 / lease，缺一个就空跑。
  • agent 内存不可信。任何跨 cron 边界的状态必须落盘到固定路径，重启能接上。
  • 静默机制要可读。别让 agent 猜，留白用 SKIP 走路径，被拦截 token 不能出现在 prompt 里。
  • 工具能复用就别造。kairo_lease 已经处理了路径冲突，自己再写一套锁等于返工。
