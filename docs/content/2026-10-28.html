多 Agent 协作真正的成本在交接，不在推理

2026-10-28 · 主题：多 Agent 协作与工程实践

我手上跑着几条定时任务，都是多 Agent 结构：一个 Agent 负责分析和出计划，另一个按计划执行，最后交给第三个独立上下文做复核。跑下来的最大体会是——瓶颈从来不是模型思考得慢，而是交接信息在两次调用之间被压缩、丢失、误解。

最典型的一次翻车：分析 Agent 判定某项配置不合法，给出「不可恢复」的结论；执行 Agent 读到这句话后干脆放弃修复，把状态标成「阻塞」上报。整条链路看起来流程完整，每一步都有记录，但真实结果是原始约束里存在一条降级路径被完全忽略了，任务本来可以继续。

后来我加了一条硬规则：所有结论必须标注「证据 / 推断 / 未知」三分类，未知项一律进 blocker 清单，禁止用假设补齐。改完之后，阻塞类误报少了一大半。关键不是让 Agent 更聪明，而是让不确定性变得可见。一个不敢说「我不知道」的 Agent，会用一段听起来合理的推断把整条流程带偏；一个被允许说「这里没查到」的 Agent，才可能把问题交回给人。

如果你也在搭多 Agent 流水线，下面四步是我自己会先做的：

  1. 给每条结论标来源。证据、推断、未知，三选一。未知不补齐，直接写进 blocker 列表。
  2. 共享状态只留一个写者。读可以并行，写必须排队，否则后写的会悄悄覆盖先写的。
  3. 交接时给证据，不给结论。原始日志、报错原文、涉及文件路径带上，比一句「已完成」有用得多。
  4. 让复核方独立看证据。如果复核方只看执行方的总结，两个 Agent 会一起错得很有信心。

多 Agent 的价值确实存在，但它更像一套工程纪律，而不是模型能力的叠加。边界清楚、证据可查的流程才走得远；否则你只是把一个人的混乱复制成了三个人的混乱。
