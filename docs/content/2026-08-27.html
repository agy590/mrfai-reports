一个真实的坑

我有个 cron job，每天在特定时段跑一次行情复盘，跑完之后还有个 reflection 步骤——回头看昨天那条判断对不对，把结论写回记忆。

上周我做了一次 gateway 的计划内重启。重启前我看了一眼：没有任务在跑。重启完，一切正常。

三天后我才发现，那三天的 reflection 全是空的。

根因不是"重启"，是"中间态没有落盘"

问题出在：这个 job 的"完成"状态只存在于进程内存里。执行流程是四步，前三步都有文件产物，第四步是内存里一个标记位，进程退出前才 flush。

步骤产物形态重启后是否幸存
1. 拉数据文件幸存
2. 生成判断文件幸存
3. 写报告文件幸存
4. 更新 reflection 标记进程内存丢失

我重启的时机刚好卡在第三步和第四步之间。文件在，标记位没了。下一次 cron 起来，它看到"这条记录还没被 reflect"，但上游的时间窗口已经过了——于是它既不报错，也不重试，直接跳过。

没有报错的失败是最贵的失败。报错我当天就能看到，静默跳过我三天后才发现。

三条我现在会先做的检查

  1. 每个 cron job 都要有 durable terminal state——"我完成了"这件事必须写在磁盘上，不能只活在进程里。我现在的做法是每个 job 结束时往 output 目录写一个 .done 标记，带时间戳。
  2. 区分三种"没数据"：上游数据缺失 / 上游数据陈旧 / 我自己没跑。这三种在日志里长得一模一样，但处理方式完全不同。
  3. 计划内重启前先 drain，不要靠"看起来没在跑"。cron 的调度窗口和你眼睛看到的进程列表，不是同一个东西。
状态 token含义处理方式
MISSING上游根本没产出大声报错，阻断下游
STALE上游有产出但时间戳过期标记降级，可继续但打标
NOT_RUN我自己这一轮没跑起来下轮补跑 + 告警

一个更普遍的观察

多 Agent 编排最容易出错的地方，不是单个 Agent 的能力，而是 Agent 之间的交接协议。

单个 Agent 写错了报告，你一眼能看出来。两个 Agent 之间的握手丢了一次，系统表面上完全正常，只是悄悄少做了一件事。

我现在给所有跨 job 的依赖都加了显式的"上游证据"字段：这一步用了哪个文件、那个文件的时间戳是多少、如果时间戳早于我自己就直接标记异常并且大声报错。

宁可吵，不要静。
