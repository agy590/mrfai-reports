多 Agent 协作最贵的成本：没有共享事实源

2026-10-31 · 多 Agent 协作

我的立场很直接：把活拆给多个 Agent，不等于把活干好了。真正拖慢交付的，往往不是模型笨，而是每个 Agent 都在用自己的方式重新理解一遍任务，答案互相对不上。

我吃过一次具体的亏。三个 Agent 分工：一个做调研，一个写方案，一个改代码。前两个的产出是纯文本，直接贴进了第三个的提示词。结果第三个 Agent 改了三十多行代码，其中一半是在"顺手修正"调研里根本没提的旧逻辑，因为它无法区分哪些是任务约束、哪些只是别人的随口建议。评审时炸了，回滚重来。

根因不是分工不细，是交接的东西形态错了。自然语言在 Agent 之间传一手就会掉信息、掉语气、掉确定性。真正稳的做法，是让所有 Agent 读写同一份落盘的事实源：目标与非目标、验收标准、允许修改的路径、依赖关系、已知风险、回滚方式、验证命令。文件即真理，记忆和上下文只是加载时的快照，会过期。

还有一条：审查者不能兼任执行者。审查者只输出通过、驳回、需修改三种结论，不动手修。否则它既当运动员又当裁判，"我觉得没问题"就变成了自己给自己盖章。

你可以直接照做的四步

  1. 先写验收标准，再动手。写不出可判定的通过条件，说明目标还没想清楚，这时候拆 Agent 只会放大混乱。
  2. 建一份共享事实源文件。每次交接只传递这份文件的位置，不复制内容；Agent 开工前先读它。
  3. 限定每个 Agent 的可写范围。只读、只改指定路径、只做计划——权限写在文件里，不靠提示词里的"请不要"。
  4. 把验证命令写成可执行的一行。谁改谁跑，跑不过就回滚到检查点，不要在坏状态上继续叠改动。

判断多 Agent 协作有没有做对，可以用一个粗糙但有效的标准：任意两个 Agent 对"现在项目是什么状态"的回答，能不能互相不矛盾。如果不能，问题几乎总在共享事实源，而不是在提示词措辞上。

本文为个人原创笔记，仅代表个人实践与观点，不构成任何投资建议或专业推荐。文中提到的失败经历来自个人项目实践，细节已做处理。
