Cron 编排最容易踩的 3 个坑——把"自动跑"变成"自动翻车"

📅 2026-08-23 · MrFai 的 Agent 笔记 · 来自真实的多 Agent 工作流

为什么写这篇

过去三个月我把 Hermes Agent 的 4 段 MGC 复测 cron + AI 日报 + 信号反思跑成了完整链路。听起来很美好，实际跑起来才发现：Cron 不是"写完 cron 配置就完了"，它是一个需要持续调试的活系统。

今天把我踩过的 3 个最深、最隐蔽的坑写出来，每个都有具体案例和修法。希望你不用像我一样，一个坑 debug 三天。

坑 #1:把"任务成功"和"任务完成"画等号

最早我判断 cron 跑没跑，就看它有没有输出文件。结果某次 MGC 复测连续"成功"输出 5 天后才发现：第 3 天开始 API 返回的是空数据，Agent 用空数据生成了"看起来正常"的报告，我也没察觉。

症状：HTTP 200 + 数据缺失 + Agent 凭"经验"生成幻觉填充。

修法:给每个输出加"健康自检"

现在每个 cron 的最后一步都强制跑一段校验,作为 Agent 的最后一条指令:

## 自检 (硬性,失败则不交付)
- 报告正文行数 > 50 ?
- 关键字段 (时间 / 价格 / 方向) 全部存在 ?
- 数据源 URL 全部 200 ?
- 任一为否 → 在交付前补 "⚠️ 数据异常" 提示

后来我加了更狠的:把"上次成功时间"写到一个状态文件,如果超过 18 小时没刷新,直接在最终输出里写"任务卡住"——不静默。

坑 #2:多个 cron 共享同一个工作目录 → 互踩

AI 日报 cron 和 MGC 复测 cron 起初都用同一个 /tmp/agent_workspace。偶尔两者几乎同时启动,会读到对方写到一半的状态文件,生成错乱的报告。更糟的是,清理 cron 会把对方正在用的临时文件删掉。

症状:间歇性内容错位,bug 完全不可复现,日志里看不到冲突。

修法:每个 cron 独占 workdir + lease

现在每个 cron 启动时强制走 lease 协议:

# 启动时
mkdir -p /tmp/cron/{job_id}/{date}
cd /tmp/cron/{job_id}/{date}  # 物理隔离

# 跨任务交接 (用 Kairo lease)
kairo_lease acquire --task signal-reflection --holder cron-{job_id}
# 用完释放
kairo_lease release --task signal-reflection
教训:Cron 不是孤岛,它运行在一个多 Agent 共存的环境里。任何"我以为不会冲突"的假设,迟早会被某个凌晨 3 点的并发执行打脸。

坑 #3:Cron prompt 越长,执行越脆弱

我曾给 MGC 复测写过一个 1500 字的 cron prompt,把"何时跑 / 怎么分析 / 怎么输出 / 风险提示"全塞进去。结果 Agent 跑出来的东西 60% 都漏掉了风险提示段落——因为 prompt 中段的内容模型注意力最弱。

症状:关键约束被忽略,LLM 优先复述开头的指令。

修法:核心约束前置 + 模板外置

  • Cron prompt 砍到 400 字以内,只写"任务定义 + 硬约束"
  • 详细输出格式 → 拆成模板文件,从磁盘 read_file 加载
  • 硬性安全门 → 写在 prompt 最开头,而不是"注意事项"小节

改完后,关键段落(风险提示 / 数据源标注)的命中率从 60% 提升到 95%+。这不是玄学,这就是 prompt 工程里"信息位置效应"的实证。

一张表总结

坑 症状 修法
成功 ≠ 完成 空数据 / 幻觉报告 健康自检 + 异常不静默
共享工作目录 间歇性错位,无法复现 独占 workdir + lease 协议
超长 prompt 中段约束被忽略 ≤400 字 + 模板外置 + 硬约束前置

最后的真话

Cron 自动化听起来高大上,实际是大量沉默的运维债务。每个 cron 都像一只宠物,你以为按下"自动喂食"就完事了——结果它第 7 天拉肚子了,你 9 天后才看见。

如果你刚开始做 Agent 编排,我的建议是:第 1 个月每天人工看一眼输出。不是不信任 Agent,是你要建立对"它什么时候会错"的直觉。这个直觉比任何监控工具都值钱。
